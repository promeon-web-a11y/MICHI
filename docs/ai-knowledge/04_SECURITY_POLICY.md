## 1. 個人情報

| 番号 | 方針 | 重要度 |
|---|---|---|
| S-1 | クレジットカード番号を MICHI で保持しない | 【MUST NOT】（原則。例外は人間の決定） |
| S-2 | 個人情報は必要最低限にする | 【MUST】 |
| S-3 | 認証情報（メールアドレス、認証に使う情報）と、公開されるプロフィール情報を分ける | 【MUST】（現状との差は Q-04） |
| S-4 | 秘密情報（APIキー、パスワード、`.env.local` の中身）を文書・チャット・ログに書き写さない | 【MUST NOT】（`CLAUDE.md` 4節） |

## 2. アクセス制御

| 番号 | 方針 | 重要度 |
|---|---|---|
| S-5 | RLS（Row Level Security）等で、行単位のアクセス制御を行う | 【MUST】 |
| S-6 | service role 等の強い権限を、クライアント（ブラウザ・アプリ）に公開しない | 【MUST NOT】 |
| S-7 | 利用者の特定は、リクエスト本文ではなく認証（JWT）で行う | 【SHOULD】 |
| S-8 | 外部APIのキーはサーバー側だけで使う | 【MUST】 |

［事実］現在の実装は S-5〜S-8 に沿っている旨が文書に書かれている（`mikke-supabase-backend/README.md`、`IMPLEMENTATION_SUMMARY.md`「安全性の要点」）。本番環境で有効かどうかは、この文書の作成時には確認していない。

## 3. 現在地

| 番号 | 方針 | 重要度 |
|---|---|---|
| S-9 | 現在地は利用してよい（周辺検索、プラン生成、現地報告の確認） | 【MAY】 |
| S-10 | 詳細な現在地を長期保存しない | 【MUST NOT】（原則） |
| S-11 | 現地にいることを確認したあとは、詳細位置を破棄し、「現地確認済み」という事実だけを保存する | 【MUST】 |
| S-12 | 利用者ごとの位置履歴（いつ・どこにいたかの連続した記録）を作らない | 【MUST NOT】 |

```text
現在地 → 周辺検索・プラン生成 → 処理終了 → 詳細位置は破棄
現地報告 → 現在地で店舗付近にいることを確認 → 詳細位置は破棄 → 「現地確認済み」だけ保存
```

- ［TODO］「長期」が何日以上か、粗い精度（例：約1km）の位置を残してよいかは未決定（Q-07）

## 4. 権限モデル

| 主体 | できること | 重要度 |
|---|---|---|
| 未ログイン | 公開情報（公開ルート）の閲覧 | 【MAY】（現状は Q-06） |
| 一般ユーザー | 閲覧、Like、Save、Comment 等 | 【MAY】 |
| 投稿者 | 自分の投稿の編集 | 【MAY】。他人の投稿の編集は【MUST NOT】 |
| MICHI運営（人間） | モデレーション（非表示、投稿停止、復元） | 【MAY】。手順は `mikke-supabase-backend/docs/moderation-runbook.md` |
| AI社員 | 担当業務に必要な範囲の分析・運営 | 【MUST】必要最小限。無制限のDB権限は【MUST NOT】 |
| 重大操作 | 人間の承認があるときだけ実行 | 【MUST】 |

### 重大操作（人間の承認が必要）

- 大量削除、重要なデータの変更・削除
- 本番データベースへの接続、migration の実行
- 権限設定・環境変数・APIキーの変更
- その他、`CLAUDE.md` 5節に挙げられた操作

承認の求め方は `CLAUDE.md` 5節のとおり（何をするか、なぜ必要か、元に戻せるか）。

### AI社員の権限

- ［事実］現在の AI社員（`.claude/agents/*.md`）が持つ道具は、ファイルの読み書きとWeb検索・取得のみ。DBへ接続する道具は与えられていない（2026-10-05 確認）
- 【MUST】AI社員に新しい権限を与えるときは、担当業務に必要な範囲に限り、読み取りと書き込みを分ける
- 【MUST NOT】AI社員に service role 相当の権限を与えない

## 5. データを失わない設計

対象は `03_DATA_POLICY.md` 6節の重要資産。原文は「段階的に導入する」としており、**導入済みであることを意味しない**。

| 手段 | 方針 | 重要度 | 現状 |
|---|---|---|---|
| 自動バックアップ | 導入する | 【MUST】 | ［TODO］設定の有無は未確認 |
| 定期 Export | 導入する。Supabase の外にも取り出せる状態にする | 【SHOULD】 | ［TODO］未確認。頻度・担当は未決定（Q-14） |
| Soft Delete | 重要資産の削除は、まず論理削除とする | 【SHOULD】 | 退会処理は hard delete（Q-03） |
| 操作ログ | 運営・AI社員による重要な操作を記録する | 【MUST】 | ［事実］通報への対応は記録が残る（moderation-runbook 2節）。それ以外は未確認 |
| Version 管理 | 必要に応じて編集履歴を持つ | 【MAY】 | ［TODO］未実装 |
| 管理者権限の制御 | 管理操作ができる人・経路を限定する | 【MUST】 | ［事実］運営操作は Supabase Dashboard の SQL Editor のみ（同 runbook） |
| 写真のバックアップ | **DBのバックアップとは別に**考える | 【MUST】 | ［TODO］未決定 |

- 【MUST】写真（Object Storage）は DB のバックアップに含まれない前提で扱う
- ［TODO］Soft Delete と「利用者が自分のデータを消せること」の両立は未決定。退会時の扱いは人間が決める（Q-03）。決まるまで、既存の `account-deletion-runbook.md` の手順を変えない

## 6. 写真・ファイル

- 【MUST】実ファイルは Object Storage、DBにはメタデータと `storage_path` を持つ
- 【SHOULD】画像はアップロード時にリサイズ・圧縮する（［TODO］現状は未確認）
- 【SHOULD】規模が大きくなったら、保存容量に加えて Bandwidth / Egress も監視する（`05` 4節）

## 7. AI社員が守ること

- 【MUST】利用者の個人情報を文書に残す前に匿名にする
- 【MUST NOT】確認していないセキュリティ設定を「設定済み」「安全」と書かない
- 【MUST】この文書に反する実装・運用を見つけたら、直さずに人間へ報告する（コードの変更は承認が必要）
