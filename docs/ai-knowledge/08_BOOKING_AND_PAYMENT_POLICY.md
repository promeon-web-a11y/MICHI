## 1. 初期の方針

| 番号 | 方針 | 重要度 |
|---|---|---|
| B-1 | MICHI 自身がクレジットカード番号を保持しない | 【MUST NOT】（原則。例外は人間の決定） |
| B-2 | AIが利用者に代わって決済しない | 【MUST NOT】 |
| B-3 | AIが利用者の確認なしに予約を確定しない | 【MUST NOT】 |
| B-4 | AIは旅行プランと予約候補を準備する | 【MAY】 |
| B-5 | 利用者本人が、予約サービス上で内容と金額を確認する | 【MUST】 |
| B-6 | 利用者本人が、最終的な予約と決済を行う | 【MUST】 |
| B-7 | 予約サイトへ遷移したことは、検証に必要なイベントとして記録する | 【SHOULD】（現状は Q-10） |

## 2. 流れ

```text
MICHI AI
 → 旅行プラン
 → 実旅行者のルート・コメントの確認
 → ホテル／体験の候補
 → 予約条件の準備
 → Review & Book Securely
 → 外部予約サービス
 → 本人による内容・料金の確認
 → 本人による予約・決済
```

- 金額・空き状況・キャンセル条件は、外部予約サービス上の表示が正である。MICHI 側の表示は「目安」「遷移先で確認」と示す【SHOULD】
- AIが金額や空き状況を推測して示してはならない【MUST NOT】（`07` A-2）

## 3. 将来的に目指すUX

［仮説］完全自動か完全手動かの二択にせず、次の形を検討する。

> **AIが95%準備し、人間が最後の5%を確認・承認する**

AIが準備するもの：ホテルの選択、日程、人数、部屋の候補、料金の比較、予約候補の決定。
人間がするもの：最終確認と決済。

- 「95%」「5%」は考え方を表す比喩で、計測する数値目標ではない（この文書を作成した Claude Code の解釈）

## 4. 完全なAI予約・決済

- ［方針］MICHI 内での完全な予約・決済は、**実際の利用者の需要と安全性を確認してから**検討する
- ［TODO］検討を始める条件（需要をどう測り、どの水準で判断するか）は未決定
- 【MUST NOT】AI社員は、予約API・決済機能の導入を確定事項として扱わない

## 5. 検証中の仮説

| 仮説 | 状態 |

| 外部予約サービスへ遷移する方式は、操作が1段階増える可能性がある | ［仮説］離脱率は未検証 |
| 「MICHIにはカード番号を渡さなくていい」ことが、安心材料になる | ［仮説］アメリカ人利用者で検証する |

## 6. AI社員の判断例

| 場面 | 対応 |
|---|---|
| 紹介文を書く | 「カード情報を預かりません」を**効果が実証された強み**として書かない。事実（保持しない）として書くのはよい |
| 収益の案を出す | Affiliate 等の条件は `10_REFERENCE.md` の手順で最新の公式情報を確認する。条件を確定事項として書かない |
| 有料サービス・提携への登録が必要 | 実行せず、人間の承認を求める（`CLAUDE.md` 5節） |
