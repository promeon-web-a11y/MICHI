## 1. MICHI は何か

- ［方針］MICHI は、単なるAI旅行プラン生成サービスではない
- ［方針］競争力の中心は「**実際に日本を旅行した外国人の実体験 × AI**」である。AIのプラン生成能力だけを競争力としない
- ［方針］「みんなのルート」は単なるSNS機能ではなく、**データ収集と推薦改善のエンジン**であり、主要なデータ資産である

## 2. 原則

| 番号 | 原則 | 重要度 |
|---|---|---|
| P-1 | MICHI を単なるAI旅行プラン生成サービスとして設計・説明しない | 【MUST NOT】 |
| P-2 | 「みんなのルート」を主要なデータ資産として扱い、その蓄積を損なう設計をしない | 【MUST】 |
| P-3 | AIだけに依存しない。実旅行者の情報・公式情報・外部データを組み合わせる | 【MUST】 |
| P-4 | 重要な事実（営業状況、英語対応、支払い方法、料金、待ち時間など）をAIに推測・捏造させない | 【MUST NOT】 |
| P-5 | 情報の種類を区別して扱い、利用者にも区別して示す（3節） | 【MUST】 |
| P-6 | 重要な最終判断（予約、支払い、行くかどうか）は利用者に残す | 【MUST】 |
| P-7 | 初期段階では、AIが利用者に代わって予約・決済しない | 【MUST NOT】 |
| P-8 | 外国人旅行者が日本で**実際に**困ることの解決を優先する | 【SHOULD】 |
| P-9 | Google Maps 等にもある情報（住所、営業時間）だけでなく、MICHI 独自の情報を蓄積する | 【SHOULD】 |
| P-10 | データが不明なときは「不明」と示す。埋めるために作らない | 【MUST】 |

## 3. 情報の種類（P-5）

次の5種類を混ぜない。

| 種類 | 例 | 扱い |
|---|---|---|
| 公式情報 | 施設・事業者が公表する情報 | 出典と確認日を持つ |
| 外部データ | Google Places 等の外部APIの情報 | 取得元と取得日を持つ |
| 実旅行者情報 | ルート、コメント、写真、Like / Save / Want to go | 誰の体験かの関係を保つ（`03`） |
| リアルタイム情報 | 混雑、待ち時間、臨時休業などの現地報告 | 報告時刻・件数・信頼度を持つ（`06`） |
| AI推論 | 並び順、組み合わせ、要約、推薦理由 | 事実として表示しない。上の4種類を根拠にする（`07`） |

## 4. 目指す循環（ネットワーク効果）

［仮説］次の循環が成り立つことを目指す。成り立つかどうかは未検証（`09_CURRENT_STRATEGY.md`）。

```text
旅行者がMICHIを使う
 → 実際に日本を旅行する
 → ルート・写真・コメントを投稿する
 → 現地情報が増える
 → 他の利用者が Save / Like / Want to go する
 → MICHI独自のデータが増える
 → AI推薦の精度が上がる
 → MICHIの価値が上がる
 → さらに旅行者が増える
```

## 5. AI社員の判断例

| 場面 | してよい | してはならない |
|---|---|---|
| 紹介文・投稿案を書く | 「実際に旅行した人のルートを参考にできる」と書く（機能が実在する場合） | 「AIがすべて決めてくれる」「AIが予約まで完了」と書く |
| デモや資料用のデータを作る | 「サンプル」と全画面で明記する | 作り物の旅行者コメントや英語対応情報を、実データのように見せる（Q-08） |
| 改善案を出す | 外国人旅行者の実際の困りごとに結びつける | 根拠のない困りごとを前提にする |
| 場所の情報が足りない | 「不明」「要確認」と示す | AIに補わせる |
