## 1. 現在の基本構成

| 領域 | 採用 |
|---|---|
| Frontend | Vercel |
| Backend | Supabase |
| Database | PostgreSQL |
| Auth | Supabase Auth |
| Photos | Object Storage |
| AI | 外部の AI API |
| Places / Routes | 必要に応じて外部API（Google Places / Routes 等） |

具体的なサービス名・モデル・料金プランは変わりうるため、`10_REFERENCE.md` に置く。

## 2. 基本方針

| 番号 | 方針 |
|---|---|
| T-1 | 2027-03-31 まで、最大1万人規模の検証を想定する |
| T-2 | 2027-03-31 の1万人規模までは、Supabase を主要バックエンドとして使う |
| T-3 | 「1万人になった」という理由だけで AWS 等へ移行しない。10万人規模でも、ユーザー数だけを理由に移行しない |
| T-4 | 無料プランに固執しない。必要に応じて Supabase / Vercel 等を有料化する |
| T-5 | 移行は、ユーザー数ではなく**性能・セキュリティ・可用性・コスト**で判断する |
| T-6 | 大規模インフラの構築より、需要の検証を優先する（`09`） |

有料プランの契約・変更は、人間の承認が必要（`CLAUDE.md` 5節「お金・契約」）。

## 3. 成長時に対応する順序

上から順に検討する。前の段階で足りるうちは、次に進まない。

```text
1. PostgreSQL（現状のまま）
2. Index 最適化
3. 集計値（原本の行は残す。03 の D-3）
4. Cache
5. Vector / Search
6. CDN・検索専用基盤
7. 必要ならインフラ再設計
```

## 4. 監視対象と移行の判断基準

| 分類 | 指標 |
|---|---|
| 容量 | DB容量、Storage |
| 通信 | Egress（Bandwidth） |
| 負荷 | CPU / Memory、同時接続 |
| 品質 | API response time、Error rate、可用性 |
| 安全 | セキュリティ上の要件を満たせるか |
| コスト | AI API cost、外部API cost、**Infrastructure / API Cost per Active User** |

- ［方針］AI・外部APIの利用量で費用が大きく変わるため、固定費だけでなく Cost per Active User を KPI として監視する

## 5. 移行可能性（ベンダー依存を避ける）

- ［方針］Supabase は現在のインフラであり、MICHI のデータ資産そのものではない
- ［方針］必要になったとき、別の PostgreSQL、AWS、GCP 等へ移せる状態を維持する
- 設計時の確認点:
  - データの意味が標準的な PostgreSQL の表・列で表現されているか
  - 写真は DB に実体を入れず、参照（`storage_path`）で持っているか
  - 定期 Export で Supabase の外に取り出せるか（`04` 5節）
  - 認証情報とプロフィールを分けているか（`04` S-3）

## 6. AI社員がこの文書を使うとき

- 技術の提案は、3節の順序と 4節の基準に沿って理由を書く
- 「ユーザーが増えたから移行する」という提案はしない（T-3, T-5）
- 金額を書くときは `10_REFERENCE.md` の手順で、その時点の公式情報を確認する
- インフラ・設定・コードの変更は行わない。案を出し、人間の承認を待つ
